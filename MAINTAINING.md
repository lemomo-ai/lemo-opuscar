# Maintaining the library

**For the repository owner only.** If you are making a film for a user, go back to [`AGENTS.md`](AGENTS.md): nothing here applies.

## Add a style

Work in `styles/<slug>/` (lowercase letters, digits, hyphens; unique). Start from the templates in `styles/_template/`.

| File | What it holds |
|---|---|
| `style.json` | the only metadata source: `slug`, `num`, `en`, `cn`, `category_en`, `category_cn`, `film`, `line`, `line_cn`, `uses`, `frame_sec`, `dur`; `film_cn`, the demo film's Chinese title (the Chinese site shows it; without it, the English title); optional `aka`, the names a renamed style had before (`styles/README.md` lists them and the site's search finds them, so an old name still finds it; they appear nowhere else); optional `needs`, a list of what a film in the style requires beyond the library, whose only value is `"image-generation"` (`NEEDS` in `styleboard/build.py`, which stops on any other): an image generator the user provides; it marks the style ✦ with a note in `styles/README.md` and in the style list in `AGENTS.md`, and adds a "Needs" row to the style's page on the site; optional `by`, `{"name", "url"}`, for a style contributed from outside: the contributor is credited after the style's name in both READMEs (also in the cards' alt text) and in a "Contributed by" row on the style's page, and `media.py --check` lists them; such a style also gets its author into `LICENSE` (the contributed styles, How to credit) and its own tables in `REUSE.toml` |
| `STYLE.md` | the style's invariants only: look, materials and rendering, colour logic, type, motion, camera grammar, sound palette, the medium's pitfalls, native moves, range of variation. No story, arc, beat table, durations or end card. Ends with a link to `DEMO.md` |
| `DEMO.md` | opens with "One example among many. Don't reuse its story, arc, shots, props or timings." Then the demo's story and structure, shot list, score structure, palette and props, end card (the "LemoLab × Claude Opus 5.5" sign-off lives only here, as the library demo's), build notes and code entry points, and for a scene style the `content.json` fields |
| `demo/` | the source, a one-command `build.sh` and `CREDITS` are committed, for agents to read. `TREATMENT.md`, `PRODUCTION_LOG.md`, fonts, audio, textures and models stay local (gitignored); `CREDITS` names every asset so it can be found again, and `build.sh` fetches the fonts first (for example `demo/tools/fonts.sh`: the same files, from URLs pinned to a commit or a version), so a fresh clone builds |
| `demo/stills/` | stills the docs link (`styleframe.jpg` is the gallery card) |
| `<slug>.mp4`, `<slug>.srt`, `poster.jpg` | the 1080p film, its subtitles when it is spoken, its poster |

Third-party assets must allow reuse, commercial use included, with at most a credit: public domain, CC0, CC BY, OFL, or a permissive code licence such as MIT or ISC (OpenStreetMap data, ODbL, only as a small credited extract); never NC or ND material. The few exceptions (the six voice tracks made with online TTS, the IBTrACS typhoon track) are named with their terms in `LICENSE` or `REUSE.toml`. Each asset is in `demo/CREDITS` with its licence. A third-party file committed to git also gets a table in `REUSE.toml` with its path, licence and copyright (a licence not used yet adds its text to `LICENSES/`); when the film is made from third-party footage, photographs, scans, imagery, map, elevation or other data, 3D models or textures, so do its poster, stills, README cards and gallery card (table 3b; one file when only that still uses such material); a picture that shows Clawd, Anthropic's character, goes in table 3c, and a picture or code that draws Clawd or redraws a third-party product's interface or logo gets `LicenseRef-Clawd` or `LicenseRef-ThirdPartyMarks` (as Mascot Screencast's do); `reuse lint` must pass ([REUSE](https://reuse.software)). No watermark on any film. Real people, brands and events appear only in an unofficial fan film; its `DEMO.md` says so.

Rules for library demos only (a user's film follows `DIRECTOR.md`, not these):

- **Bilingual subtitles, one line per language.** Each cue has one Chinese line and one English line, never wrapped. When a line is too long, split it into two cues.
- **Comparisons hold still before the verdict.** When the film compares options (four bridges, three plans), each one is fully in frame and held at least 2.5 s before it is judged, so the viewer can read it.

## Register

1. **Number.** `num` in `style.json` is the next free number after the highest in `styles/*/style.json` (a string: the next is `"100"`; until its release a new style may keep `""`, which sorts last; the 99 styles of the 2026-11 release were numbered 01–99 in the gallery's order); it orders the gallery within a category. Add the style to `NEW` in `styleboard/gallery.py` (the newest release's styles, marked "New"), and at a release replace that list with the release's own styles.
2. `sh styleboard/frames.sh <slug>` (the gallery card from `demo/stills/styleframe.jpg`). Then `python3 styleboard/build.py` reads every `styles/*/style.json` and rewrites `styleboard/catalog.json`, `styleboard/anchors.json` (the site's old anchors → its stations), the counts and the generated parts of `README.md` (English) and `README.zh-CN.md` (Chinese), `styles/README.md` and the style list in `AGENTS.md`. In the READMEs, between `<!-- styles:start -->` and `<!-- styles:end -->`, it writes a line of contents and, per category (a station on the site's workbench), a small heading (`###### 02 · Painting & Illustration`, with the old anchor `#painting--illustration` kept in it), the station's header picture linked to `#s02` on the site, its one line on the look (`CAT_DESC` in `styleboard/gallery.py`), one card per style linked to the style's page (the Chinese README links `/zh/`) and the names as text with any contributor's credit; between `<!-- thanks:start -->` and `<!-- thanks:end -->`, the thank-you films (`THANKS` in `gallery.py`) as cards. Never edit those generated parts by hand. The rest of the two READMEs is written by hand: change both together (e.g. the 🆕 lines: keep the latest two or three).
   Then `node styleboard/art/readme.mjs` draws the pictures they show into `docs/readme/` (each in English and Chinese, for GitHub's light and dark themes): the cover (four seconds of the site's long take, an animated WebP; `docs/cover.jpg` is its still for readers without `<picture>`), a header per station, a card per style (from `styles/<slug>/poster.jpg`), OPUSCAR 98 and the thank-you cards, the end plate that asks for a star (the bench's lamps, from frame 95 of the long take), and `docs/social.jpg` (GitHub's social preview, also the site's share card: upload it by hand in the repository's Settings → Social preview whenever it changes). It is incremental: `docs/readme/manifest.json` keeps a key per picture, and only pictures whose inputs changed are drawn again. Renaming a style redraws its four cards; adding one redraws its station's four headers (they show the count), its own cards and the cards after it in that station (a card's gutters depend on its column); a new poster redraws that style's cards; the covers carry no count and stay. `styleboard/art/readme.json` holds what `build.py` and `readme.mjs` must agree on (folder, columns). The headers, covers, OPUSCAR 98 and end plates and `cover.jpg`/`social.jpg` are drawn from the site's renders (the station stills, the long take's first 33 frames and frame 95, the projector frame), which will live on the site media release (not made yet); until then pass their folder with `--media` or `OPUSCAR_MEDIA` (default `.release/site-source`, which git ignores; a symlink does). Without it, pictures that need no redrawing are kept, and one that does stops the run and names the file it needs, so on another machine new styles' cards draw from the repository alone. Needs playwright-core's Chromium, ffmpeg, cwebp and img2webp (libwebp), python3. Fonts (OFL), the site's: Source Serif 4, Source Sans 3, Noto Serif SC and Noto Sans SC, pinned in `styleboard/fonts/fetch.py` and downloaded on first use. `python3 tools/release.py check` fails when the READMEs name a picture that isn't there, when `docs/readme/` holds one no README names, or when either README weighs more than 4 MB to open.
3. `sh tools/web_cuts.sh` makes the 720p web cut in `.release/web/` (only for films that are new or changed).
4. **Site text.** In `styleboard/i18n.json`: the Chinese for each of the style's `uses` in `uses_cn` (the style page shows them as "Good for"), and in `about` one sentence on what the style looks like, in English and Chinese, drawn from STYLE.md §1 (the look, not the demo's story); `build.py --site` stops when either is missing. Also its use tags in `tag_of` (1–3 of the ids in `tags`): the site no longer shows them, but they stay for agents choosing a style. The styles listed in `NEW` in `styleboard/gallery.py` count as new (a small "New" on their cards); replace the list at a release.
5. **Site media.** `python3 styleboard/media.py --films .release/web` makes the new film's posters, stills, ruler sprite, card thumbnail and hover clip in the site's media folder (only what changed), then measure its label (**The site**). The long take isn't rendered again: a new style joins its station as a card.

## The site

The GitHub Pages site, the Workbench, is built by `build.py --site` with `styleboard/pages.py` and `styleboard/home.py`: the home page (a long take along a workbench, one station per category), one page per style, OPUSCAR 98, the thank-you films and a 404 page, in English at `/` and in Chinese at `/zh/` (every page has its twin; the 404 page holds both), plus `llms.txt`, `sitemap.xml` (both languages) and `opuscar98/styles.json`. The design rules and a map of its files are in `styleboard/DESIGN.md`. Each page carries its canonical link, `hreflang` pairs, share-card tags and JSON-LD (upstream repo and author). Counts come from the data and lengths from the films themselves; the feature's runtime is `FEATURE['dur']` and the thank-you films are `THANKS`, both in `gallery.py`. The old site's anchors (`styleboard/anchors.json`, the table the README uses too) and file addresses (`posters/`, `stills/`, `img/…`, `films/`) keep working. What a fork or a renamed repository changes (repository, site address and path, where the films load from) is in one file, `styleboard/site_config.py`.

**Media.** Posters, stills, the players' ruler sprites, OPUSCAR 98's frames, the cards' thumbnails and clips and the home page's long take are not in git (about 250 MB). `python3 styleboard/media.py --films .release/web` makes and updates them in the media folder, remaking only what a changed film or poster touches (`--media DIR`; default `site_config.MEDIA`: `.release/site-media`, which git ignores and may be a symlink, or `$OPUSCAR_SITE_MEDIA`). The long take (`manifest.json`, `vid/`, `still/`) was rendered for the site and changes only when it is rendered again. `sh tools/site_media.sh` packs the folder into `site-media.tar` and checks it; `sh tools/site_media.sh --upload` puts it on the `site-media` release, which `pages.yml` downloads. If the `site-media` release doesn't exist yet, create it (`gh release create site-media --title "Site media" --notes "…"`) and upload the tar before the site is first pushed, or CI stops at its "media" step.

**Where the films load from.** GitHub Pages documents 1 GB per site, and the 720p cuts alone weigh about 1 GB, so they are split (`styleboard/site_config.py`, `film_url`). The styles' demo films (about 860 MB) load from the films repository, [`lemomo-ai/lemo-opuscar-films`](https://github.com/lemomo-ai/lemo-opuscar-films): a public repository that holds only them and serves them with its own GitHub Pages, at `https://lemomo-ai.github.io/lemo-opuscar-films/<slug>.mp4` (`FILMS_BASE`). OPUSCAR 98, the thank-you films and the "My style" demo stay in the site, at `films/` (`pages.yml` downloads them from the `web` release). A style film's old address in the site, `films/<slug>.mp4`, reaches `404.html`, which sends it on.
- **Update it** after `tools/publish.sh` has made the web cuts: `sh tools/films_repo.sh` copies every style's cut into a local checkout of the films repository (default `../lemo-opuscar-films`, or give the folder; it refuses any other git checkout, this repository included): it adds new films, replaces changed ones, removes those of styles that are gone, writes the repository's `README.md`, `LICENSE` (the CC BY 4.0 text), `.nojekyll` and `.gitignore`, and writes `styleboard/films_repo.json` here, the list of what the repository holds (commit it). Look at what changed, then `sh tools/films_repo.sh --push` commits those files only and pushes whatever origin lacks, a commit left by a failed push included (it prints what it pushes first; nothing is pushed without `--push`). Push it before `main`, so the site never plays a film that isn't there yet.
- **Checks:** `check_site.py` fails when a page plays a style film that `films_repo.json` doesn't list, when the list was made for another address than `FILMS_BASE`, or, on a machine with `.release/web`, when a cut there differs from the listed one (the films repository is behind). In CI, a later step of `pages.yml` asks the films repository's Pages for every listed film (200, `video/mp4`, the listed size) and deploys nothing when one is missing, so the site online stays as it was.
- **History:** every changed film stays in the films repository's git history, which only grows. Now and then flatten it: an orphan branch with the current files, then a force push (`git checkout --orphan new && git add -A && git commit -m "Films" && git branch -M new main && git push --force origin main`); the script never does that by itself. GitHub frees the old history's space some time after the force push, not at once.
- **Set up once:** create the public repository `lemomo-ai/lemo-opuscar-films`, clone it to `../lemo-opuscar-films`, run `sh tools/films_repo.sh --push`, then turn on Pages for it (Settings → Pages: deploy from the `main` branch, root folder).
- **Preview** with every film inside the site: build with `OPUSCAR_FILMS_BASE=films/` (below).

**Labels.** A style page's label and its top bar sit on the film; each poster is measured so they stay readable. After adding a style, build and serve the site, run `node styleboard/labelcheck.mjs --base http://127.0.0.1:8000/ --out <media>/label-rects.json`, then `python3 styleboard/media.py --labels` (it writes `labels.json`, which sets each page's scrim), and build again. `python3 styleboard/media.py --check` prints the per-style report: missing films or posters, stills moved off a bad frame, former names, contributors, STYLE.md headings that aren't the usual ones.

Preview locally (OPUSCAR 98 and the thank-you films linked from `.release/web`, the style films from the films repository; media hard-linked from the media folder). With `OPUSCAR_FILMS_BASE=films/` before `build.py`, the style films are linked from `.release/web` too, and the preview works offline. **Preview with `styleboard/serve.py`, not `python3 -m http.server`:** films need byte ranges to seek, unknown addresses must get `404.html` as on GitHub Pages, and the 404 page's `<base>` needs the site's own path (`/lemo-opuscar/`) to work.

```sh
python3 styleboard/build.py --site _site --films .release/web      # add --media DIR when it isn't the default; OPUSCAR_FILMS_BASE=films/ in front to keep every film local
python3 styleboard/check_site.py _site
python3 styleboard/serve.py 8000                                   # http://127.0.0.1:8000/ and /zh/ (also /lemo-opuscar/)
```

The build needs fontTools and brotli for the font subsets (in the Python that runs it, or the `fonttools` command on `PATH`); Source Serif 4, Source Sans 3, Noto Serif SC and Noto Sans SC are pinned in `styleboard/fonts/fetch.py` (one google/fonts commit, with their SHA-256) and downloaded once into its cache. `media.py` needs numpy, Pillow and ffmpeg with libsvtav1. In CI, `pages.yml` downloads OPUSCAR 98, the thank-you films and the "My style" demo from the `web` release into `_site/films` and `site-media.tar` into `_media`, builds with `--films _site/films --media _media` (with `GITHUB_TOKEN`, to read the star count the top bar shows; without a token, or offline, the bar says GitHub without a number and the build goes on), then runs `check_site.py` (it also checks that every style page runs on into its language's bench, `media/bench-<lang>.json`, which the build writes): every page has its twin, no local link or anchor is broken, every film a page plays has its meta.json, sprite and posters and is in the site or listed in `styleboard/films_repo.json`, the media bundle is unpacked, the text colours meet WCAG AA, and no published file names a path on the building machine.

## Gates

- **Human:** approve the style frame before production, and the finished film.
- **Machine:** `asr_check.py` passes on every line; `mux.sh` reports about −14 LUFS and no warning; `readcheck.mjs` passes; `python3 tools/release.py check --strict <slug>` is clean (it needs the Register steps above). It also stops images under `styles/` that no committed file names (by name or pattern), demo files that nothing reached from the style's entries (STYLE.md, DEMO.md, build.sh, index.html…) loads, and process wording (`PRODUCTION_LOG`, review notes; the list is `PROCESS_WORDS` in the script) in any committed text.
- **Maps:** library demos follow DIRECTOR.md §13 like any film: every map shot checked enlarged, the map data and its view named in `CREDITS`.
- **Real events and products:** every fact on screen and in the voice-over comes from an official source, kept in `demo/FACTS.md` (claim, URL, quoted wording); check the final script against it before the last render.

## Publish

The first time: create the `site-media` release and upload the media (**The site**, Media), and set up the films repository (**The site**, Where the films load from: Set up once).

1. `sh tools/publish.sh` uploads the full films (`films` release) and the 720p web cuts (`web` release, used by the site), then verifies them. Per-demo resource packs are no longer published. When the site's media changed, `sh tools/site_media.sh --upload` too (**The site**).
2. When a style's film was added, changed or removed: `sh tools/films_repo.sh`, look at what it changed, then `sh tools/films_repo.sh --push` (the films repository goes before `main`; **The site**, Where the films load from).
3. Before pushing `main`, make sure the films repository's Pages serve the new films: `curl -sI https://lemomo-ai.github.io/lemo-opuscar-films/woodcut.mp4` (or a film that changed) answers 200 with `content-type: video/mp4`. The first deployment of a new repository can take several minutes or more.
4. `git status --short`, `git add -A` (with `styleboard/films_repo.json`), commit.
5. Push `main`, then watch CI (`gh run watch`): the site build fails when a film has no media in `site-media.tar`, a page plays a film that isn't on the `web` release or in `styleboard/films_repo.json`, the films repository doesn't serve a listed film, or `check_site.py` finds a broken link or a page without its twin.

Don't push before the upload has finished, and don't commit `tools/assets.json` from a failed run.

## Revise a style

Back up first (old versions move out of the repository, not into git). Re-render, replace `<slug>.mp4`, and run `sh tools/publish.sh`: it re-uploads the film and refreshes its web cut.

## Directory edition

The Claude plugin directory lists a self-contained build of the plugin, on the orphan branch `directory` (the submission tracks that branch; `main` stays what visitors see). It carries the guides, every `STYLE.md` / `style.json` / `DEMO.md`, `core/` (without the Poly Haven models, which only demo code uses) and its own `README.md`, `SECURITY.md` and `SKILL.md`: nothing is cloned or fetched to tell the agent what to do, there are no demo sources, and Chinese edge-tts narration is used only with the user's consent. The sources of the plugin-only files are in `tools/directory/`; the build and its checks (file sizes, personal info) are in `tools/directory.py`.

After a release on `main` (new styles, changed guides or tools):

1. `git worktree add ../lemo-opuscar-directory directory` (once; reuse it afterwards).
2. `python3 tools/directory.py <version> --into ../lemo-opuscar-directory`, with a version above the branch's current `.claude-plugin/plugin.json` (new styles or features: 1.1.0; fixes only: 1.0.1). The directory treats each version number as a release, so the script refuses the same or a lower one; `--same-version` is only for fixing a version that was never published. It also stops when a guide changed so much that one of its edits no longer applies: update `EDITS` in the script.
3. `claude plugin validate ../lemo-opuscar-directory`, then commit there (`Lemo-Opuscar <version>, plugin directory edition`) and push `directory`. The directory scans each push and publishes the new version.
